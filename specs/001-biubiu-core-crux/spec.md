# Feature Specification: biubiu-core 可移植业务核心 + 授权撤销试点迁移

**Feature Branch**: `001-biubiu-core-crux`

**Created**: 2026-09-03

**Status**: Draft

**Input**: User description: "参考 vela-wallet 中 crux 的用法，用 Rust 创建一个 biubiu-core 来管理业务规则、业务状态和逻辑；需要把现有 biubiu.tools 下的业务逻辑都迁移过去；使用 GitHub Spec Kit 工作法。"

## 背景与问题

`apps/biubiu.tools` 有 15 个工具应用，业务规则分散在各自的 Svelte store 里。同一类正确性问题在每个 store 中被各自重新解决，语义互不相同：

- **陈旧响应保护**：`pda-apps/revoke/store.svelte.ts` 用私有 `scanGen` 单调计数器；`updown-shared/stores/fetch-coordinator.ts` 用另一套协调机制；多数 store 没有任何保护。
- **加载/失败/回滚状态**：每个 store 各写一份 `scanning` / `error` / `finally` 三元组，且「哪个请求拥有 spinner」的判断各不相同。
- **业务规则与 I/O 混住**：`revokeRows()` 同时持有「撤销后从表中移除行」的规则与「6 秒后自动收起成功横幅」的定时器；前者是业务，后者是平台。

后果是这些规则**无法被测试**——验证「切链后旧扫描结果不得落到新链」需要真实浏览器、真实网络与真实时序。也**无法被复用**——同一份规则要进第二个平台就得重写一遍。

本 feature 建立一个平台无关的业务核心，并用一个真实业务域证明这条边界成立。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 业务规则可在无浏览器条件下被证明 (Priority: P1)

维护者需要在不启动浏览器、不连网络、不等待真实时间的前提下，证明一条业务规则成立。今天做不到：所有规则都嵌在 Svelte 组件/store 的异步流程里。

**Why this priority**：这是整个 feature 的目的。没有这一条，后面的迁移只是把代码换个地方放。

**Independent Test**：在核心的测试套件中给定一个业务状态与一个业务事件，断言产生的新状态与对外请求；整个套件在无网络、无浏览器、无真实时钟的环境下运行完毕。

**Acceptance Scenarios**：

1. **Given** 一个已扫描出若干授权的业务状态，**When** 收到「撤销选中项成功」事件，**Then** 这些行从状态中移除、选中集合同步清空，且断言过程不涉及任何网络或计时。
2. **Given** 一次扫描正在进行中，**When** 用户切换到另一条链、随后先前那次扫描才返回结果，**Then** 该结果被丢弃，状态中不出现另一条链的数据。
3. **Given** 一次扫描正在进行中，**When** 先前那次扫描以失败返回，**Then** 不产生任何错误提示（陈旧失败同样不得改变状态）。

---

### User Story 2 - 授权撤销的用户可见行为完全不变 (Priority: P1)

授权撤销工具的使用者在迁移前后感知不到差异：同样的链切换、自动扫描、筛选、选择、单条/批量撤销、成功与失败提示。

**Why this priority**：迁移的价值全部建立在「不破坏现有功能」之上。行为一旦漂移，这次迁移就从改善变成了风险。

**Independent Test**：对照迁移前的行为清单逐项操作页面，确认每一项一致；现有的该域测试断言在新核心中有等价用例且通过。

**Acceptance Scenarios**：

1. **Given** 钱包已连接且停在默认链，**When** 页面加载完成，**Then** 自动发起一次扫描，且同一「所有者 + 链」组合不会重复自动扫描。
2. **Given** 已有扫描结果，**When** 用户切换链，**Then** 结果、选择、错误、上次撤销结果全部清空，并在新链上重新自动扫描。
3. **Given** 筛选为「仅无限额度」，**When** 用户点击「全选可见」，**Then** 只有当前可见的行被选中。
4. **Given** 选中若干行，**When** 批量撤销成功，**Then** 这些行消失、成功提示出现、约 6 秒后自动收起；**And** 失败提示不会自动收起，须由用户关闭。
5. **Given** 一次撤销正在进行中，**When** 用户再次触发撤销，**Then** 第二次请求被忽略，不产生并发撤销。
6. **Given** 用户添加了一个自定义代币/授权方，**When** 保存该条目的持久化失败，**Then** 本次会话仍然可用该条目，且随即重新扫描。

---

### User Story 3 - 新增一个业务域的成本是可预期的 (Priority: P2)

维护者迁移下一个域时，只需描述该域的状态、事件与对外请求，不需要再写一遍事件泵、请求编号、取消传播、合约声明。

**Why this priority**：这决定了后续 14 个域的迁移是线性成本还是每次重来。它依赖 P1 建立的骨架，因此排在其后。

**Independent Test**：以文档记录接入一个新域所需的步骤与改动点，并由 revoke 域的实际接入过程验证该清单完整。

**Acceptance Scenarios**：

1. **Given** 骨架已就位，**When** 接入一个新业务域，**Then** 前端侧只需声明该域的核心构造器、初始事件、视图订阅与请求执行器，不需要新增任何事件循环代码。
2. **Given** 核心侧的状态或事件类型发生变化，**When** 执行常规的开发或构建命令，**Then** 前端使用的类型声明自动同步，无需手工修改。

---

### User Story 4 - 未迁移的域不受影响 (Priority: P1)

其余 14 个工具应用在本次变更后行为与构建方式完全不变。

**Why this priority**：宪法原则 VI 要求增量与并存。若引入核心必须一次性改动全部域，这次迁移就无法安全落地。

**Independent Test**：在本 feature 的任意一次提交上构建并运行应用，逐一打开其余工具页面确认可用。

**Acceptance Scenarios**：

1. **Given** 核心已引入，**When** 构建整个应用，**Then** 构建成功且其余工具页面行为不变。
2. **Given** 开发者未安装本地额外工具链，**When** 执行既有的开发命令，**Then** 得到明确的前置条件说明，而不是一个难以定位的构建失败。

---

### Edge Cases

- **钱包未连接**：无所有者时不得发起扫描，页面呈现待连接状态。
- **扫描期间连续切链**：只有最后一次切换对应的扫描结果可以落地；中间各次全部丢弃。
- **撤销进行中切链**：结果仍然落地并弹出提示（沿用迁移前行为，见 research.md D14）。
- **空选择撤销**：不产生任何对外请求。
- **自定义网络无可用 RPC**：以「需要 RPC」的明确结论返回，不添加网络。
- **添加已存在的链**：直接选中已有网络，不产生重复条目。
- **删除当前选中的自定义网络**：回退到默认链并按切链规则清空状态。
- **成功提示自动收起前用户手动关闭**：不得在稍后再次改变提示状态。
- **持久化（本地存储）失败**：属于非关键路径，不得影响主流程。

## Requirements *(mandatory)*

### Functional Requirements — 业务核心骨架

- **FR-001**: 仓库 MUST 包含一个平台无关的业务核心组件，承载业务规则、业务状态与状态转换。
- **FR-002**: 该核心 MUST NOT 执行网络请求、持久化、计时、随机数生成或任何平台调用；这些一律以「请求」的形式交给宿主执行。
- **FR-003**: 核心对外声明的每一项请求 MUST 只描述意图，MUST NOT 包含端点地址、超时、重试策略或凭据。
- **FR-004**: 每一项跨宿主的请求 MUST 由核心分配相关性标识并记录为在途状态；结果返回时若该标识不在在途表中、或其关联目标与结果不符，该结果 MUST 被丢弃且 MUST NOT 改变任何状态。
- **FR-005**: 宿主与核心之间的数据契约（事件、视图、请求、结果）MUST 由核心侧定义并自动生成宿主侧的类型声明；生成产物 MUST NOT 被手工编辑。
- **FR-006**: 契约生成 MUST 在常规开发与构建流程中自动执行，MUST NOT 依赖开发者记得手动触发。
- **FR-007**: 宿主侧的事件泵（分发事件、执行请求、回送结果、取消传播）MUST 是与具体业务域无关的共享实现，每个域 MUST NOT 各写一份。
- **FR-008**: 核心的默认构建 MUST NOT 包含状态机能力所需的依赖；该能力 MUST 是默认关闭的可选开关。
- **FR-009**: 核心产物 MUST 有体积上限门禁，超出时构建 MUST 失败并给出实际数值。

### Functional Requirements — 授权撤销域（试点）

- **FR-010**: 核心 MUST 拥有授权撤销的完整业务状态：当前网络、扫描结果、扫描中/已扫描/扫描失败、筛选条件、选中集合、撤销中/撤销阶段/撤销失败、上次撤销结果、批量 gas 结算资产、逐行进行中标记、自定义网络/代币/授权方。
- **FR-011**: 系统 MUST 在同一「所有者 + 链」组合下只自动发起一次扫描；切换链后 MUST 视为新的组合。
- **FR-012**: 切换网络时，系统 MUST 使在途扫描失效，并清空扫描结果、已扫描标记、扫描错误、选中集合、上次撤销结果与已选 gas 结算资产。
- **FR-013**: 筛选为「仅无限额度」时，可见行 MUST 只包含额度实际上无上限的行；「全选可见」MUST 只作用于当前可见行。
- **FR-014**: 撤销进行中时，系统 MUST 忽略新的撤销触发；空行集合的撤销 MUST NOT 产生对外请求。
- **FR-015**: 撤销成功后，系统 MUST 从结果中移除对应行并从选中集合中移除对应标识。
- **FR-016**: 撤销成功提示 MUST 在约 6 秒后自动收起；撤销失败提示 MUST 持续到用户关闭。收起的计时 MUST 由宿主执行，其到期 MUST 作为一个事件回到核心。
- **FR-017**: 用户手动关闭提示时，系统 MUST 取消尚未到期的自动收起，使其之后不再改变提示状态。
- **FR-018**: 添加或移除自定义代币/授权方后，系统 MUST 重新扫描；其持久化失败 MUST NOT 影响本次会话的可用性。
- **FR-019**: 按链标识添加自定义网络时：该链已存在则 MUST 直接选中而不新增；元数据可获取则据此填充，不可获取则以链标识兜底；无任何可用 RPC 且未提供覆盖值时 MUST 以「需要 RPC」的明确结论失败。
- **FR-020**: 移除当前选中的自定义网络时，系统 MUST 回退到默认网络并执行切链的全部清空规则。
- **FR-021**: 每一行的稳定标识 MUST 在核心内生成，规则与迁移前一致，使宿主的逐行状态在重新扫描后仍能对上。
- **FR-022**: 撤销请求 MUST 以「撤销这些行」的形式交给宿主；具体交易的构造与签名 MUST 留在宿主，MUST NOT 进入核心。

### Functional Requirements — 迁移约束

- **FR-023**: 迁移后该域的宿主状态容器 MUST 只持有核心返回的视图，MUST NOT 保留任何派生的业务结论。
- **FR-024**: 迁移前该域测试所覆盖的每一条业务断言 MUST 在核心侧有等价用例；原测试 MUST NOT 在等价用例通过前被删除。
- **FR-025**: 本次变更 MUST NOT 修改其余 14 个工具应用的行为。
- **FR-026**: 本次变更 MUST NOT 夹带对该域的功能改进；迁移中发现的缺陷 MUST 记录为独立条目留待后续处理。
- **FR-027**: 构建该核心所需的本地工具链 MUST 有文档说明与前置检查；缺失时 MUST 给出可执行的修复指引而非原始构建错误。

### Key Entities

- **业务域核心（Domain Core）**：一个业务域的状态与规则的所有者。接收事件、更新状态、产出「渲染」或「请求」。
- **业务状态（Model）**：某一域的全部内部状态，包含在途请求表。不对外暴露。
- **视图（ViewModel）**：核心对外呈现的、供渲染使用的状态投影。含派生结论（如「现在能否撤销」），但不含在途请求编号等内部记账。
- **事件（Event）**：进入核心的唯一入口。来源为用户操作、宿主返回的结果、或宿主的计时到期。
- **请求（Operation）**：核心对宿主的一句请求，如「扫描这条链上这个所有者的授权」。携带相关性标识。
- **结果（ShellResult）**：宿主对一次请求的应答，携带同一相关性标识。
- **授权行（ApprovalRow）**：一条当前生效的授权，由标准、代币、授权方唯一确定，标记是否为无限额度。
- **撤销网络（Network）**：可扫描的链，含读取端点、区块浏览器、聚合器地址，区分内置与自定义。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 授权撤销域的全部业务规则可在一条不联网、无浏览器的命令下完成验证，整套用例在 10 秒内跑完。
- **SC-002**: 迁移前该域测试中的业务断言，100% 在核心侧有对应用例且通过。
- **SC-003**: 迁移后，授权撤销页面的用户可见行为与迁移前逐项一致，差异数为 0（记录在案的缺陷修复不计入，且本次不做修复）。
- **SC-004**: 该域宿主状态容器中不再存在任何业务判断分支；其代码量相对迁移前下降，且下降部分可逐条对应到核心中的规则。
- **SC-005**: 「切链丢弃陈旧扫描结果」这一规则在核心中有且仅有一处实现，宿主侧不存在任何代次计数器或请求身份比较。
- **SC-006**: 其余 14 个工具应用在本次变更后全部可正常构建与使用。
- **SC-007**: 接入下一个业务域所需的宿主侧新增代码，不包含任何事件循环、请求编号或取消传播逻辑。
- **SC-008**: 核心产物体积有明确上限并在构建中被检查；本次的实际数值被记录，作为后续变更的对照基准。

## Assumptions

- **架构选型已由宪法确定**：核心以 Rust + Crux 实现，宿主为 SvelteKit Web，契约由代码生成。本 spec 因此在描述规则时不再重复论证该选型；具体的 crate 划分、API 与构建接线属于 plan 阶段。
- **目标平台仅 Web**：本次不产出 iOS/Android 绑定，但核心不得引入会阻断未来添加它的依赖。
- **试点域为授权撤销（revoke）**：选它是因为它同时具备陈旧响应保护、宿主计时器、单条/批量两条策略路径与已有测试可作对照，且不牵扯费用报价、价格源与交易编码。
- **交易构造与钱包签名留在宿主**：核心只表达「撤销这些行」的意图。把 ABI 编码与 Safe/EIP-5792 差异搬入核心不在本次范围。
- **自定义数据的持久化留在宿主**：核心持有这些数据的业务含义与去重规则，读写由宿主执行。
- **其余 13 个域的迁移不在本次范围**：它们由后续 spec 逐个覆盖，本次只需保证其不受影响并验证接入成本可预期。
- **开发者需具备本地 Rust 工具链**：由文档与前置检查覆盖；CI 的构建环境接线属于 plan 阶段决定。
