# Phase 0 Research: 批量代币发送域迁移

**Feature**: `002-token-sender-core` | **Date**: 2026-09-03

spec 001 的 D1–D14 继续适用，不再重复。本文件只记录 token-sender 特有的决策。

---

## D15 — 批次编排：核心一次只请求一批，由结果推进

**Decision**：核心不持有循环。它的 Model 里有一张批次表；每收到一个批次结果，就更新该批状态并
**决定要不要发出下一批**。整轮发送因此是一串「请求 → 结果 → 请求」，而不是一条执行流。

```text
迁移前（宿主，一条执行流从头持有到尾）
  for (i of batches) {
     if (aborted) break
     if (completed.has(i)) continue
     if (sent > 0) await delay(2500)     ← 占住执行流
     await wallet.sendBatch(chunk)        ← 一次 passkey
  }

迁移后（核心，无循环）
  StartSend / Resume  ──► 选出「下一个待发批次」──► 请求 SendBatch{ id, index, … }
  BatchSucceeded{id}  ──► 记录结果 ──► 若还有待发批次 ──► 请求 DelayThenContinue{ id, ms }
  DelayElapsed{id}    ──► 选出下一个待发批次 ──► 请求 SendBatch{…}
  BatchFailed{id}     ──► 记为可重试 ──► 同上（沿用「跳过」策略）
  Pause               ──► 只是把 running 置否；不撤回任何在途请求
```

**Rationale**：这不是把循环换个写法。`CLAUDE.md` 自己记着这条教训：

> 用 `await sleep()` 实现延迟是**同步思维** —— 当前执行流暂停等待。延迟应该**持久化为状态**，
> 而不是阻塞执行流。

`runSend` 正是那个反例，而且代价是真实的：整轮发送（可能上百批、每批一次 passkey 确认、
批间 2.5 秒）由一条执行流持有，**进度只存在内存**。关页面即遗忘。

改成状态机后，「哪些批次已成功」变成核心 Model 里的一张表，而不是某个 `for` 作用域里的
局部数组。它是否**持久化**是下一个 spec 的事（本次不做，FR-019），但没有这一步，那件事根本
无从谈起。

**Alternatives rejected**：
- **让核心发出「跑完整轮」的单个请求，宿主内部循环**：核心就此丧失批次粒度的状态，
  「不重发已成功批次」这条金钱安全规则又回到宿主的循环里 —— 与迁移的目的相反。
- **核心一次发出全部批次请求，宿主并发执行**：每批要一次 passkey 确认，并发等于同时弹出上百个
  系统弹窗。串行是产品要求，不是实现限制。

## D16 — 暂停：停止发出新请求，绝不撤回在途请求

**Decision**：`Pause` 只把 Model 的 `running` 置否。**在途批次的请求不被撤回**，其结果回来时
照常记录。`cancelled_effect_ids` 依然恒为空。

**Rationale**：这是 spec 001 D9 结论的第二次印证，而且这次的代价更明确 —— **交易可能已经上链**。
撤回一个已发出的 `sendBatch` 请求，等于让核心不再知道那批钱到底发出去没有；下次续发时它会被
当作「未成功」重发，**对同一批地址打两次款**。

宿主侧的 `AbortController` 因此从这个域消失。迁移前它同时承担两件事：中断批间延时、以及在
循环顶部提前退出。前者由核心不再发出下一个延时请求实现，后者由核心不再选出下一批实现。

**批间延时的中断**是唯一需要「立即生效」的部分（FR-007）：用户在 2.5 秒间隔中点暂停，不该等满。
做法与 spec 001 的自动收起一致 —— 延时是一个带 id 的请求，暂停时把它移出在途表；宿主的定时器
照常到期，回来时因 id 不在表中被丢弃。**宿主依旧不需要保存定时器句柄。**

**Alternatives rejected**：
- **用 AbortSignal 中断在途的 sendBatch**：见上，会造成重复打款。
- **暂停时清空批次表**：那正是迁移前刷新页面的效果，也正是要修的问题。

## D17 — 收件人解析进核心；十万级输入的性能作为独立条目

> **本条关于 `getAddress` 的部分已被 D21 推翻。** 下面「校验和留在宿主」的论证基于一个错误
> 前提（以为 viem 的 `isAddress` 默认宽松），实测后核心改为自己做 EIP-55 校验。保留原文是为了
> 让那次推翻有据可查。其余部分仍然成立。

**Decision**：`parseRecipients` 的全部规则搬进核心：分隔符、注释行、地址去重（保留首次）、
两种分配模式、非法原因分类、均分模式的余尘归属。地址的**校验和格式化**（`getAddress`）留在宿主。

**Rationale**：解析产出的每一个数字都直接决定用户看到的金额与被收取的费用 —— 有效数、重复数、
总额、批次数、总费用。这是业务，不是格式转换。

`getAddress` 留在宿主，是因为它是 EIP-55 校验和计算（需要 keccak256）。把它搬进核心要引入一个
哈希 crate，而核心真正需要的只是「这是不是一个合法地址」与「小写形式用于去重」——两者都不需要
校验和。这与 spec 001 D4 对 `unlimited` 的处理是同一条判据：**核心要不要理解链上数值/编码**。

**须实测的风险**：迁移前解析是同步的，设计文档提到十万级输入将来要移入 Web Worker。搬进核心后，
解析发生在 WASM 里、跨 JSON 边界传回。**十万行文本的一次往返成本必须实测**；若成为瓶颈，
记录为独立条目（可能的方向：分块解析、或只回传摘要而不回传全部收件人）。

**Alternatives rejected**：
- **解析留在宿主，只把结果送进核心**：那么「重复地址算不算数」「非法行怎么分类」这些规则就留在
  宿主，而它们直接影响总额。
- **连 `getAddress` 一起搬**：为一次校验和引入哈希 crate，且不让任何规则变得更可测。

## D18 — 会员费用豁免：核心只拥有「已证明 ⇒ 为 0」

**Decision**：链上会员状态查询与 passkey 控制权证明留在宿主。核心拥有的是两条规则：
单批费用在豁免成立时为 0；豁免状态变化时费用必须重算。

**Rationale**：迁移前的注释写得很清楚 ——「仅在本会话已 passkey 签名证明控制权后才为真 ——
防观察钱包/复制 session 绕过」。这是一条**安全规则**，它的载体是一次签名，而签名属于宿主。

核心该拥有的是它的**后果**：费用归零、以及「证明成功后必须重算」这条时序规则。迁移前后者
藏在 `waiveFeeWithPasskey` 的 `if (this.step === 3) await this.prepareReview()` 里 ——
一个与当前步骤耦合的副作用，换个入口就可能漏掉。

## D19 — 网络表：与 revoke 同样由宿主供给，但这次它是本域自己的

**Decision**：token-sender 的内置网络表（`infra/networks.ts` 的 `listNetworks()`）**搬进核心**。

**Rationale**：这与 spec 001 D12 的结论**不同**，而判据是同一条。revoke 的网络表逐条派生自钱包的
`CHAINS`（`slug` 就是钱包的 `apiNetworkId`），属于尚未迁移的 wallet 域。token-sender 的网络表
是**这个域自己维护的**：它带着 `maxBatchNative` / `maxBatchErc20` / `multiSendAddress` 这些
只有批量发送才关心的字段，没有别的域读它。

而这些字段**直接参与业务规则**：每批上限决定批次数，批次数决定总费用。把它们留在宿主，
「250 个收件人分几批、总共收多少费」这条规则就无从测起。

D12 那条判据因此站得住：**本域拥有的数据进核心，别的域拥有的由宿主供给。** 两个域给出相反的
结论，恰好说明判据是可判定的，而不是一句口号。

## D20 — 体积：第二个数据点，以及一个已经预备好的应对方向

**Decision**：迁移完成后测量 release WASM，与 spec 001 的两个数值并列记入 `results.md`，
并据新实测值重设门禁。

**已知的对照基准**（spec 001 实测）：

| 构成 | 字节 |
|---|---:|
| 骨架 + 一个最小占位域 | 142,255 |
| 骨架 + revoke 域 | 322,553（+180,298，+127%） |

**判读方式**：revoke 的增量里有相当一部分是内置注册表的字符串数据（约 100 条代币/授权方）。
token-sender 的网络表小得多（十来条），但它多了解析器与批次编排。

- 若增量**明显小于** revoke，说明 revoke 的体积主要来自注册表数据，**后续域不会线性放大**；
  应对方向是注册表数据改为运行时按链拉取（vela-wallet 的 i18n catalog 正是这个结论）。
- 若增量**接近或超过** revoke，说明成本来自 serde 对每个线类型的单态化，**会线性放大**；
  那时该考虑的是缩减线类型数量或换一种边界编码，而不是数据的承载方式。

**这个判读要在测到数值之后再下**，不要提前假设。

### 实测结果（2026-09-03）与判读

| 构成 | 字节 | 增量 |
|---|---:|---:|
| 骨架 + 一个最小占位域 | 142,255 | — |
| ＋ revoke 域 | 322,553 | +180,298 |
| ＋ sender 域 | **553,101** | **+230,548** |

**第二个数据点推翻了第一个的猜测。** spec 001 当时写的是「revoke 的增量里有相当一部分是内置
注册表的字符串数据（约 100 条代币/授权方，含名称与标签）」。如果那是主因，sender 应该**明显更
小** —— 它的数据表只有 9 条网络。

结果 sender 加了 **+230K，比 revoke 还多 28%**。所以主导成本不是数据，是**每个域自己的机器**：

- serde 为每个线类型单态化出的序列化/反序列化代码。sender 有 24 个事件、9 个 operation、
  13 个结果、外加约 20 个值类型 —— 每一个都要一份 `Serialize` 和 `Deserialize`。
- 该域自己的逻辑：解析器、批次编排。
- `tiny-keccak`（本次新增，未单独测量）。

**因此它会随域数大致线性增长。** 剩下 12 个域按每个 ~200K 估，还要再涨 ~2.4MB —— 加上现在的
540KB，会到 3MB 量级。那是首屏必须下载的东西。

**这是一个需要现在就做的决定，不是可以推到最后的优化。** 但它也**不属于本 spec**（迁移不夹带
改进）。已记入 `results.md` 作为独立条目，可能的方向按代价从低到高：

1. **按域切分 WASM**：每个页面只加载它需要的那个域。代价是多个 wasm 产物与多份 crux 运行时
   （骨架 142K 会被重复计入），但用户实际下载量下降最多。
2. **缩减线类型数量**：sender 的 24 个事件里有相当一部分是纯 setter（`SetRecipientsText` 等），
   可以合并成一个带字段名的通用事件。代价是合约的自解释性下降。
3. **换边界编码**：放弃 JSON 改用更紧凑的格式，省掉 serde_json 的一部分单态化。代价是 spec 001
   D3 论证过的可观测性与 ts-rs 合约一致性。

方向 1 与本仓库的形态最契合（每个工具是独立页面），但它会改动 spec 001 建立的通用层，
需要一个自己的 spec。

## D21 — EIP-55 校验进核心（实现期实测纠正 D17）

**Decision**：核心依赖 `tiny-keccak`（`crux` feature 下），在解析时做 EIP-55 校验和验证，
并输出带校验和的地址形式。

**Rationale**：D17 原本写的是「核心需要的只是『这是不是合法地址』，不需要 keccak256」。
那个前提**是错的**，实测 viem 才发现：

| 输入 | `isAddress(addr)` |
|---|---|
| 全小写 | 接受（无大小写信息，无从校验） |
| 正确校验和 | 接受 |
| 校验和错误（混合大小写） | **拒绝** |
| 全大写 | **拒绝** |

迁移前 `core/parse.ts` 调用的正是不带选项的 `isAddress(addr)`，即严格模式。我最初按「宽松」
实现成只查形状，那会让**全大写和笔误地址静默变成有效收件人** —— 在一个批量打款的路径上，
「这个地址是不是打错了」正是用户最需要的那道拦截。

（注意 `revoke` 域用的是 `isAddress(addr, { strict: false })`，两个域口径本来就不同，
各自保持各自的。这也说明这类判断只能逐处读代码确认，不能凭一处推断另一处。）

既然 keccak256 已经为校验而在核心里了，顺带产出校验和形式的地址也是免费的 —— 而那正是
迁移前 `getAddress(addr)` 的产出，是用户在界面上看到的那一串。

**成本**：`tiny-keccak` 是无依赖树的独立实现（不引 RustCrypto 全家桶），且挂在默认关闭的
`crux` feature 上。体积影响并入 D20 的实测。

## D22 — 读实现不够，必须读既有测试（实现期教训）

写完解析器、7 个用例全绿之后，去对照迁移前的 `core/parse.spec.ts`，发现**漏了三条规则**：

1. **第五个非法原因** `amount-too-small-for-recipient-count`：均分模式下总额 < 收件人数时，
   每份取整为 0，**整次解析被拒**。源码注释写明这是修过的一个 footgun —— 零额转账照样烧 gas、
   照样按批收费，却什么都没转。
2. 均分模式下总额缺失或不可解析 ⇒ 返回空结果（不是按 0 均分）。
3. 输出地址是 `getAddress` 的校验和形式，不是原样回传。

三条都不在我读过的那段实现主干里：第 1、2 条在 `if (mode === 'equal')` 块内的提前 return 里，
第 3 条藏在 `recipients.push({ address: getAddress(addr) })` 的一次函数调用中。

**教训**：搬迁一个域时，**既有测试是规则清单，源码只是其中一种表述**。测试里那句
「the footgun the finding describes」记录了一次真实事故；只读实现读不出那段历史，也就不会
意识到那个提前 return 是有意为之，而不是可以简化掉的分支。

spec 001 的 FR-024 要求「迁移前测试的每一条业务断言在核心侧有等价用例」—— 这条要求的价值
在这里第一次体现为**发现遗漏**，而不只是事后核对。
