# Feature Specification: 批量代币发送域迁移 —— 阻塞循环变状态机

**Feature Branch**: `002-token-sender-core`

**Created**: 2026-09-03

**Status**: Draft

**Input**: 承接 `001-biubiu-core-crux`。把 `apps/biubiu.tools` 的第二个业务域（token-sender）
迁入 `biubiu-core`，并给出 WASM 体积的第二个数据点。

## 背景与问题

授权撤销（spec 001）迁移后，骨架已经证明可用：桥与宿主泵在整个实现期未被改动，接入成本可预期。
token-sender 是第二个域，它带来一个 revoke 没有的形态问题。

`core/orchestrator.ts` 的 `runSend` 是一个**阻塞式编排循环**：

```
for (let i = 0; i < batches.length; i++) {
  if (signal.aborted) break;
  if (completedBatchIndices?.has(i)) continue;
  if (results.length > 0) await abortableDelay(2500, signal);   ← 占住执行流
  await wallet.sendBatch({...});                                 ← 一次 passkey 确认
}
```

整轮发送（可能上百批、每批一次 passkey 确认、批间 2.5 秒间隔）**由一条执行流从头持有到尾**，
进度只存在 `store.results` 这个内存数组里。后果：

- **发送中途关闭页面或刷新，已成功的批次被彻底遗忘。** `results` 与 `parsed` 一并消失，
  「继续发送」按钮不再可用；用户只能重新录入全部收件人再发一遍 —— **对已打款地址重复打款**。
  `DESIGN.md` 承诺过 TaskHub 断点续传，代码里没有。
- 「不对已完成批次重复发送、不重复收费」这条**金钱安全规则**写在循环里的一行 `continue`，
  验证它需要真实钱包、真实交易和一次真实中断。

这与 `CLAUDE.md` 自己记下的教训是同一条：**延迟与进度应当持久化为状态，而不是占住执行流**。

本 feature 把这个循环变成状态机：核心一次只请求**一批**，每批的结果作为事件回到核心并推进到
下一批。批次进度因此成为**核心拥有的状态**，而不是某条执行流的局部变量。

**本次仍是等价迁移**：进度的持久化（关页面后仍可续传）**不在范围内**，它是迁移之后的一次
独立变更（宪法原则 VI）。本 spec 只保证迁移后行为与迁移前逐项一致，并把这个缺口记录在案。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 已打款的地址永远不会被重复打款 (Priority: P1)

用户发送到 500 个地址、分成 5 批。第 3 批失败，用户点「继续发送」。前两批**不得**被重新发送，
费用也**不得**被重复收取。

**Why this priority**：这是本域唯一会造成**资金损失**的规则。它今天是循环里的一行
`continue`，从未被自动化验证过。

**Independent Test**：给定一个已有若干批次成功的业务状态，触发续发，断言核心只为**未成功**的
批次发出请求，且每个请求携带的费用与首轮一致。整个断言不涉及网络与钱包。

**Acceptance Scenarios**：

1. **Given** 5 个批次中第 0、1 批已成功、第 2 批失败，**When** 用户续发，**Then** 核心只为
   第 2、3、4 批发出请求，第 0、1 批一个请求都不发。
2. **Given** 同上，**When** 续发进行中，**Then** 已成功批次的结果保持不变，不被覆盖也不被清空。
3. **Given** 一次续发再次失败，**When** 用户第三次续发，**Then** 依然只重试仍未成功的批次。

---

### User Story 2 - 发送是可暂停、可续、逐批推进的状态 (Priority: P1)

用户在发送中途点「暂停」。**已经发出的那一批必须跑完**（交易可能已上链），但不再开始新的批次；
之后可以从暂停处继续。

**Why this priority**：暂停语义直接关系到「这一批到底发出去没有」。把它写成状态机才能保证
「不开始新批」与「不中断在途批」是两件事。

**Independent Test**：在一个批次在途时触发暂停，断言核心不再发出新的批次请求；随后送回该批的
结果，断言它被正常记录而不是被丢弃。

**Acceptance Scenarios**：

1. **Given** 第 2 批在途，**When** 用户暂停，**Then** 核心不再发出第 3 批的请求。
2. **Given** 同上，**When** 第 2 批的结果回来，**Then** 它被记录为成功，**不**被当作陈旧结果丢弃。
3. **Given** 已暂停，**When** 用户继续，**Then** 从第 3 批开始，第 2 批不重发。
4. **Given** 批次之间有约 2.5 秒的间隔，**When** 用户在间隔中暂停，**Then** 立即停止，不等满间隔。

---

### User Story 3 - 向导与费用规则可在无浏览器条件下证明 (Priority: P1)

维护者能在不起浏览器、不连网络的前提下，验证四步向导的推进条件、批次规划与费用计算。

**Why this priority**：这些规则决定用户**看到的金额**与**实际被收取的费用**，却分散在十几个
派生 getter 里。

**Independent Test**：`cargo test`，断言给定输入下的批次数、每批费用、总费用与各步骤的可推进性。

**Acceptance Scenarios**：

1. **Given** 250 个有效收件人、原生代币、该网络每批上限 100，**When** 计算批次规划，
   **Then** 得到 3 批，且总费用为单批费用 × 3。
2. **Given** 用户已通过本会话的签名证明其会员身份，**When** 重算费用，**Then** 每批费用为 0。
3. **Given** 选择 ERC20 但尚未成功读取代币元数据，**When** 判断能否离开第一步，**Then** 不可推进。
4. **Given** 解析结果中有效收件人为 0，**When** 判断能否离开第二步，**Then** 不可推进。

---

### User Story 4 - 用户可见行为完全不变 (Priority: P1)

批量发送工具的使用者在迁移前后感知不到差异：四步向导、地址解析与去重、费用展示、余额预检、
逐批进度、暂停/继续、历史记录、自定义网络与 RPC 覆盖。

**Why this priority**：迁移的价值建立在不破坏现有功能之上，而本域直接经手用户资金。

**Independent Test**：对照迁移前的行为清单逐项验证；迁移前该域测试的每一条业务断言在新核心中
有等价用例。

**Acceptance Scenarios**：

1. **Given** 一段含重复地址、非法地址与注释行的收件人文本，**When** 解析，**Then** 有效数、
   重复数、非法行清单与总额与迁移前逐字一致。
2. **Given** 均分模式与一个总额，**When** 解析，**Then** 每人所得与余尘归属与迁移前一致。
3. **Given** 切换网络，**When** 观察状态，**Then** 代币元数据、解析结果与已选 gas 结算资产被清空。
4. **Given** 一次发送全部成功 / 部分失败 / 全部失败，**When** 写入历史，**Then** 三种状态的判定
   与迁移前一致。

---

### User Story 5 - WASM 体积的第二个数据点 (Priority: P2)

维护者需要知道「每加一个域，产物长多少」，以判断后续 12 个域是否会线性放大体积。

**Why this priority**：spec 001 只有一个数据点（骨架 142,255 → 加 revoke 322,553，+127%），
无法据此外推。第二个数据点决定要不要现在就改变注册表数据的承载方式。

**Independent Test**：迁移完成后测量 release WASM，与 spec 001 的数值对照并记录。

**Acceptance Scenarios**：

1. **Given** token-sender 已入核心，**When** 构建 release WASM，**Then** 实测值被记录，
   且门禁按新实测值重设。

---

### Edge Cases

- **收件人为空 / 全部非法**：不得进入发送，不得产生任何请求。
- **批次上限为 0 或负**：批次规划必须按至少 1 的批量处理，不得产生空批或死循环。
- **暂停后立刻继续**：不得跳批，也不得重发在途批。
- **续发时全部批次都已成功**：不产生任何请求。
- **切链后原有解析结果仍在**：必须清空 —— 精度可能变了，金额含义随之改变。
- **会员身份在费用已算出之后才被证明**：费用必须重算为 0。
- **历史写入失败**：属于非关键路径，不得影响发送结果的呈现。
- **自定义网络的 RPC 覆盖被清空**：回退到该网络的内置 RPC 列表。

## Requirements *(mandatory)*

### Functional Requirements — 批次编排

- **FR-001**: 核心 MUST 拥有批次进度：总批数、已成功批次及其结果、失败批次及其原因、当前进行中的批次。
- **FR-002**: 核心 MUST 一次只请求一个批次；下一批的请求 MUST 由上一批结果的到达触发。
  MUST NOT 存在一个跨批次的阻塞循环。
- **FR-003**: 续发时，核心 MUST NOT 为已成功的批次发出请求。
- **FR-004**: 每个批次请求 MUST 携带与首轮一致的单批费用；续发 MUST NOT 改变任一批次的费用。
- **FR-005**: 用户暂停时，核心 MUST 停止发出新的批次请求，且 MUST NOT 撤回已发出的批次请求。
- **FR-006**: 已发出批次的结果 MUST 被正常记录，即使它在暂停之后才返回。
- **FR-007**: 批次之间的间隔 MUST 由核心声明其时长、由宿主执行计时；用户在间隔中暂停时
  MUST 立即停止，不得等待间隔结束。
- **FR-008**: 单个批次失败 MUST NOT 中止整轮发送（沿用「跳过」策略）；失败批次 MUST 被记录为可重试。

### Functional Requirements — 向导、解析与费用

- **FR-009**: 核心 MUST 拥有四步向导的当前步骤与各步的可推进条件。
- **FR-010**: 收件人解析 MUST 在核心内完成：按行解析、忽略空行与注释行、地址去重（保留首次）、
  区分「指定金额」与「均分」两种模式，并产出有效数、重复数、非法行清单与总额。
- **FR-011**: 解析规则 MUST 与迁移前逐字一致，包括分隔符、非法原因分类与均分模式下的余尘归属。
- **FR-012**: 批次规划 MUST 按当前网络与代币类型对应的每批上限切分；批次数 MUST 为有效收件人数
  除以每批上限向上取整。
- **FR-013**: 总费用 MUST 为单批费用乘以批次数。会员身份成立时单批费用 MUST 为 0。
- **FR-014**: 会员身份 MUST 仅在本会话完成控制权证明后成立；证明成功 MUST 触发费用重算。
- **FR-015**: 切换网络或代币类型 MUST 清空代币元数据、解析结果与已选 gas 结算资产。

### Functional Requirements — 迁移约束

- **FR-016**: 迁移后该域的宿主状态容器 MUST 只持有核心返回的视图。
- **FR-017**: 迁移前该域测试所覆盖的每一条业务断言 MUST 在核心侧有等价用例；原测试 MUST NOT 在
  等价用例通过前被删除。
- **FR-018**: 本次变更 MUST NOT 修改其余 13 个工具应用的行为，也 MUST NOT 修改 revoke 域。
- **FR-019**: 本次变更 MUST NOT 夹带对该域的功能改进 —— 包括**发送进度的跨会话持久化**，
  它是一次独立的后续变更。发现的缺陷 MUST 记录为独立条目。
- **FR-020**: 交易构造（MultiSend 打包、ERC20 编码）、钱包签名与发送、余额读取 MUST 留在宿主。
- **FR-021**: 接入本域 MUST NOT 需要改动 spec 001 建立的通用层（桥、宿主事件泵、契约生成）。
  若必须改动，该改动 MUST 被识别为通用能力并回补到通用层。

### Key Entities

- **发送计划（SendPlan）**：一次发送的不可变输入 —— 网络、代币、收件人、每批上限、单批费用。
- **批次进度（BatchProgress）**：每个批次的状态（待发 / 在途 / 成功 / 失败）及其结果。
- **收件人（Recipient）**：地址与金额。均分模式下金额由核心计算。
- **解析结果（ParseResult）**：有效收件人、重复数、非法行清单、总额。
- **费用报价（FeeQuote）**：单批费用及其是否因会员身份而为 0。
- **预检结果（PreflightResult）**：余额是否足够，以及缺口说明。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 「已成功批次不重发、不重复收费」这条规则在核心中有专门用例，且验证过程不涉及网络、
  钱包与真实交易。
- **SC-002**: 核心中不存在跨批次的循环；批次推进完全由结果事件驱动，可在用例中逐批断言。
- **SC-003**: 迁移前该域测试中的业务断言，100% 在核心侧有对应用例且通过。
- **SC-004**: 该域宿主状态容器中不再存在业务判断分支；`AbortController`、`await` 延时与批次循环
  从宿主消失。
- **SC-005**: 用户可见行为与迁移前逐项一致，差异数为 0（记录在案的缺陷不计入，本次不修）。
- **SC-006**: 其余 13 个域与 revoke 域行为不变，既有测试全部通过。
- **SC-007**: 接入本域未改动 spec 001 的通用层；若有改动，已回补为通用能力并说明。
- **SC-008**: release WASM 实测值被记录，与 spec 001 的数值并列，足以判断增长是否线性。

## Assumptions

- **承接 spec 001 的全部架构决策**：Rust + Crux 核心、JSON 边界、`ts-rs` 契约、宿主事件泵。
  D1–D14 继续适用，不再重复论证。
- **进度持久化不在范围内**：迁移后「关页面即丢失已完成批次」的行为与迁移前一致。这是一个已知的
  资金安全缺口，记录在案，作为下一个 spec 的首要候选。
- **交易构造与签名留在宿主**：核心只表达「发送这一批」的意图，与 spec 001 对撤销的处理一致。
- **会员身份的链上查询与签名证明留在宿主**：核心只拥有「已证明 ⇒ 费用为 0」这条规则。
- **价格与余额读取留在宿主**：核心不做 256 位算术之外的链上语义（沿用 research.md D4）。
- **收件人上限**：迁移前的解析是同步的，设计文档提到十万级输入将来要移入 Web Worker。本次不改变
  这一点；若核心侧解析在大输入下成为瓶颈，作为独立条目记录。
