# Phase 0 Research: 发送进度跨会话持久化

**Feature**: `003-send-progress-durable` | **Date**: 2026-09-03

spec 001 的 D1–D14 与 spec 002 的 D15–D23 继续适用。本文件只记录本 feature 特有的决策。

---

## D24 — 持久化先于花钱：落盘回执是发送的前置条件

**Decision**：核心推进到某一批时，**先**发出 `PersistSendProgress`，只有收到
`progress_persisted { ok: true }` 才发出该批的 `SendBatch`。落盘失败则暂停发送。

```text
dispatch_next_batch()
  ├─ 选出下一批 i，batches[i] ← InFlight{ id }
  ├─ 请求 PersistSendProgress{ pid }            ← 先落盘
  └─ ProgressPersisted{ pid, ok: true }  ─► 请求 SendBatch{ id, index: i, … }
     ProgressPersisted{ pid, ok: false } ─► status ← Paused，告知用户；**不发送**
```

**Rationale**：这一条决定了「未知区间」是否完整。

若落盘晚于发送，崩溃窗口正好落在「已发出、未落盘」之间时，磁盘上那一批仍是 `Pending`——
恢复后它会被当作从未尝试而**自动重发**。那正是本 feature 要防的重复打款，只是把窗口从
「整轮」缩小到「一批」而没有消除。

先落盘则最坏情况是：磁盘上记着 `InFlight` 而交易其实没发出去。那是**安全的一侧** ——
它进入「未知」流程，由确认或用户裁决，不会被自动重发。

代价是每批多一次 IndexedDB 写（毫秒级）。一批本来就要一次 passkey 确认（秒级），
这个代价可以忽略。

**这条规则的一般形式**：**当一个动作不可撤销时，关于它的记录必须先于它本身。**

**Alternatives rejected**：
- **发送后落盘**：见上，把重复打款的窗口从整轮缩小到一批，没有消除。
- **只在批次完成时落盘**：等价于上一条，且崩溃在批间时会丢掉刚成功那一批的记录。
- **不落 `InFlight`、只落终态**：恢复后无法知道有一批曾被尝试，退化成上一条。

## D25 — 在途批次恢复为「未知」，绝不猜测

**Decision**：新增 `BatchState::Unknown { hint: Option<String> }`，**只由恢复产生**。
它 MUST NOT 出现在 `next_pending_index` 的候选集里。

```text
落盘中的 InFlight ──恢复──► Unknown{ hint }
                              ├─ 请求 ConfirmBatch{ id, index, hint }
                              │    ├─ Confirmed{ tx_hash }   ─► Succeeded
                              │    ├─ NotOnChain             ─► Failed（可重试）
                              │    └─ Unresolved             ─► 保持 Unknown
                              └─ Unknown 需要用户显式裁决：
                                   「已确认未到账，重发这一批」 ─► Failed
                                   「已到账，标记完成」        ─► Succeeded
```

**Rationale**：崩溃瞬间那一批的真实状态**就是未知的**。类型系统应当如实表达这一点，而不是
用 `Pending` 或 `Succeeded` 去近似它 —— 那两个近似各自对应一种资金事故：

| 近似 | 后果 |
|---|---|
| 当作 `Pending` | 自动重发 ⇒ **重复打款** |
| 当作 `Succeeded` | 跳过 ⇒ **漏发一批**，钱没到却记为完成 |

`Unknown` 不参与自动候选，是这条设计的全部安全性所在。它和 `Succeeded` 一样是**候选集的
定义问题**，不是一句需要记得写的判断（spec 002 D15 的同一手法）。

**为什么保底路径必须存在**：凭据不总是拿得到（外部钱包的批次标识、网络不通、确认超时）。
一个「大多数时候能自动判定」的机制，若在判定不了时悄悄退回猜测，就等于没有这条设计。

**Alternatives rejected**：
- **只做自动确认，不留 `Unknown`**：确认失败时无处可去，只能猜。
- **让用户在恢复时统一确认所有批次**：把可以自动判定的也推给用户，且用户无从判断 39 批
  里哪些真的成了。

## D26 — 交易凭据必须在结果之前落盘，这要求扩宽钱包层的回调

**Decision**：把批次的交易凭据在**收到最终结果之前**落盘。为此，宿主的发送适配器需要在
`submitting → waiting` 之间把凭据回传给核心。

**Rationale**：这是 D25 的自动判定能成立的前提。事实依据：
`apps/biubiu.tools/src/lib/auth/safe-tx/send-contract-call.ts` 里

```ts
onStatus('submitting');
const userOpHash = await sendUserOperation(...);   // ← 凭据在这里就有了
return waitReceipt(userOpHash, chainId, onStatus, ...);  // ← 结果在这之后
```

`userOpHash` 在等待收据**之前**就存在，只是当前 `onStatus(status: SendStatus)` 的签名
把它丢掉了。加宽这个回调（多一个可选的凭据参数）就能把它带出来。

**范围与代价**：这是一次**钱包层的改动**，触及 `safe-tx` 与各钱包后端。它不属于「迁移」，
而是本 feature 需要的新能力，因此在范围内。但它对外部钱包（EIP-5792）路径不一定可得 ——
拿不到就是 `None`，走 D25 的保底路径。

**Alternatives rejected**：
- **不落凭据，全靠用户裁决**：可行且安全，但把本可自动完成的事全推给用户；
  40 批里有一批未知时，用户无从判断。
- **恢复时用「收件人首地址 + 金额」去链上反查**：不可靠 —— 同一组转账可能来自别的交易，
  且需要遍历区块。凭据是确定的，反查是猜测。

## D27 — 记录同时只保留一份，全部终态后清理

**Decision**：磁盘上最多一份未完成发送记录，键固定。开始新发送即替换；全部批次达到终态
（成功/失败，**不含未知**）后删除。

**Rationale**：多份记录会立刻带出一串产品问题：列表怎么排、哪一份该被恢复、两份计划的收件人
重叠怎么办。这些都不是本 feature 要解决的，而「同时只有一次发送在进行」也符合当前的串行语义
（每批一次确认，同时最多一批在途）。

**未知批次不算终态** —— 记录必须留着，否则用户下次打开就再也看不到那一批需要裁决。

**Alternatives rejected**：
- **保留历史上所有未完成记录**：见上，带出的问题多于解决的。
- **把未完成记录合进既有的 `send-history`**：历史是**已完成**发送的汇总，语义不同；
  混在一起会让「哪些能恢复」变成一次筛选而不是一次读取。

## D28 — 落盘不是瓶颈；卡住测试的是别的东西（实现期实测）

plan.md 把「十万级计划落盘约 4.5MB，写入耗时」列为风险第 1 项。实测结果是**它根本不慢**：

| 收件人数 | 快照大小 | 写 | 读 |
|---:|---:|---:|---:|
| 1,000 | 0.08 MB | 2 ms | 1 ms |
| 10,000 | 0.84 MB | 3 ms | 3 ms |
| 100,000 | **8.41 MB** | **16 ms** | **23 ms** |

（实际大小是 8.41MB，不是估的 4.5MB —— 快照除收件人外还带着批次表与计划。）

端到端也通：`send()` → 首批落盘并发出 ≈ 2,335 ms（其中落盘 16 ms，其余是 1000 个批次的
状态构造与序列化），崩溃 → 恢复 ≈ 2,126 ms，恢复后在途那批正确变成 `unknown = [0]`，
视图 35 KB（1000 条批次状态，收件人清单不在里面）。

**因此 D24「落盘先于发送」的代价可以忽略** —— 一批本来就要一次 passkey 确认（秒级）。

### 但第一次测出来是失败的，原因值得记下

第一版实测跑出 `restored = false`，看起来像「大计划存不进去」。真正的原因是**我的测试等待
窗口不够**：光解析 10 万行就要 2.4 秒（spec 002 D23 实测），而我只给了 6 秒去走完
「解析 + 报价 + 预检 + 发送 + 落盘」。

差点据此得出「持久化在大规模下不可用」的结论，进而去做一个不需要的优化（把计划与批次状态
拆成两条记录）。**分开量一次**（直接调 `writePendingSend`）才看清楚落盘只花 16ms。

教训：一个复合路径失败时，先把它拆开分别量，再下结论。否则很容易把「测试写得不对」误判成
「系统做不到」，然后去优化一个本来就不慢的东西。

## D29 — IndexedDB 连接必须关闭（实现期发现）

`pending-send.ts` 最初每次 `openDB()` 之后不关闭连接。后果在集成测试里立刻显形：
`deleteDatabase` 被打开的连接**阻塞**，后续 `open` 也挂住 ⇒ 落盘永不返回 ⇒
按 D24，那一批**永远不会被发送**。9 个用例因此失败，表现是「sendCalls 为空」。

这不只是测试问题：留着连接同样会阻塞将来的 schema 版本升级，让页面卡在打开数据库那一步。
每次操作后 `db.close()`；这个 store 每次只读写一条记录，连接复用省不下什么。

值得注意的是**这个 bug 的表现完全不像它的原因**：症状是「一批都没发出去」，而根因在
「上一次测试留了个连接没关」。D24 那条「发送以落盘为前置」把一个存储层的疏漏放大成了
功能完全停摆 —— 这是那条设计的代价，也说明落盘路径本身必须足够健壮。
