## 2. 性能实测

### 落盘本身（`writePendingSend` / `readPendingSend` 直接测）

| 收件人数 | 快照大小 | 写 | 读 |
|---:|---:|---:|---:|
| 1,000 | 0.08 MB | 2 ms | 1 ms |
| 10,000 | 0.84 MB | 3 ms | 3 ms |
| 100,000 | **8.41 MB** | **16 ms** | **23 ms** |

plan.md 把「落盘耗时」列为风险第 1 项。**它不是瓶颈** —— 16 ms 相对一次 passkey 确认
（秒级）可以忽略。D24「落盘先于发送」的代价因此是可以接受的。

### 端到端（十万收件人 / 1000 批）

- `send()` → 首批落盘并发出 ≈ **2,335 ms**（其中落盘 16 ms，其余是 1000 条批次状态的构造与序列化）
- 崩溃 → 恢复完成 ≈ **2,126 ms**
- 恢复后 `restored = true`、`unknown_batches = [0]`（在途那批正确变成未知）
- 视图 **35 KB**（1000 条批次状态；收件人清单不在里面）

### WASM 体积

| 构成 | 字节 | 增量 |
|---|---:|---:|
| 骨架 + revoke + sender（spec 002 末） | 558,032 | — |
| ＋ 发送进度持久化 | **613,163** | **+55,131** |

这是**一次能力增量**（一个新状态、四个 operation、五个结果、一个快照类型），不是一个新域。
+55K 与 spec 002 判读的「每域约 +200K」不矛盾，反而佐证了那个判读：成本主要来自**线类型的
数量**，而不是逻辑的复杂度。

门禁：`MAX_BYTES = 797,112`（实测 × 1.3）。

## 4. 实现期发现（详见 research.md）

| # | 发现 | 怎么发现的 |
|---|---|---|
| D24 | 落盘必须**先于**发送，否则崩溃窗口里那一批会被当作从未尝试而自动重发 | 设计期 |
| D25 | 在途批次恢复为 `Unknown`，不参与自动候选；确认不了就交给用户，**绝不猜** | 设计期 |
| D26 | `userOpHash` 在等待收据之前就有 —— 加宽钱包层回调把它带出来 | 读 `send-contract-call.ts` |
| D28 | 落盘根本不慢（16ms）；第一次测出来失败是**我的等待窗口不够** | **分开量一次** |
| D29 | IndexedDB 连接不关会阻塞 `deleteDatabase`，进而让一批都发不出去 | **9 个用例同时失败** |
| — | `in_flight` 在请求发出前就登记了 —— 那张表在说谎 | **测试跑红** |

D28 那一条值得记住：一个复合路径失败时先把它拆开分别量。差一点就据此得出「持久化在大规模下
不可用」，然后去优化一个本来就不慢的东西。

D29 那一条则显示了 D24 的代价：「发送以落盘为前置」把一个存储层的疏漏（连接没关）放大成了
功能完全停摆。这条设计要求落盘路径本身足够健壮。

## 5. 已知限制（不是缺陷，是设计边界）

### L-01｜外部钱包的批量路径拿不到凭据

EIP-5792 的 `wallet_sendCalls` 在等待结果之前只有一个 bundle id，它不是交易哈希，而查询它
需要 provider —— 恢复发生在新的页面加载时，钱包可能还没连上。

因此**外部钱包发送时，崩溃后那一批一定走「由用户裁决」**，不会被自动确认。这是如实的降级
（research.md D25/D26），不是失败路径：用户看到明确说明和两个动作，而不是一个被猜出来的结果。

biubiu passkey Safe 走 bundler，`userOpHash` 可得，能自动判定。

### L-02｜不做跨标签页协调

同时开两个标签页各自发送不在本次范围内。**恢复提示读的是磁盘**（不是内存），所以第二个
标签页开始发送会替换记录，第一个标签页的进度会被覆盖。

真要支持需要一把跨标签页的锁（Web Locks API），那是一次独立的变更。

### L-03｜陈旧计划不自动过期

只显示计划的创建时间，由用户判断是否还适用。设定过期时限（「三天前的计划自动丢弃」）需要
单独的产品判断 —— 一份旧计划里未发的批次仍然是欠着的钱，自动丢弃可能比保留更危险。

## 6. 发现但未修

### D-01｜`send-history` 与未完成记录之间没有关联

一次发送若在崩溃后被丢弃，它已成功的那些批次不会进入历史（历史只在整轮结束时写一条）。
用户因此在历史里看不到那次部分完成的发送。

**为什么不在这里修**：它需要决定「部分完成的发送在历史里长什么样」—— 是一条 partial 记录、
还是每批一条？这是产品问题，且与本 feature 的资金安全无关。

### D-02｜确认只查交易哈希，不查 userOp 收据

`executeConfirmBatch` 目前用 `getTransactionReceipt` 查凭据。对 biubiu 路径而言凭据是
`userOpHash`，严格说应当查 bundler 的 `eth_getUserOperationReceipt`。当前实现下它会查不到
而回报 `unresolved` —— **安全但保守**：能自动判定的场景被漏掉了一部分。

**为什么不在这里修**：接 bundler 需要知道该链的 bundler 端点，那是 wallet 域的配置。
保守回报 `unresolved` 不会造成资金事故，只是多问用户一次。修它是一次明确的小改进。
