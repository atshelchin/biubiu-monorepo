# Feature Specification: 发送进度跨会话持久化

**Feature Branch**: `003-send-progress-durable`

**Created**: 2026-09-03

**Status**: Draft

**Input**: `specs/002-token-sender-core/results.md` §7 的 D-01 —— 本仓库当前已知的、可能造成
资金损失的第一优先缺陷。

## 背景与问题

spec 002 把批量发送的批次进度变成了核心拥有的状态：一张 `Vec<BatchState>`，`Succeeded` 是终态，
「不重发已成功批次」是候选集的定义。但**那张表不落盘**。

后果：一次上百批的发送进行到第 40 批时，用户刷新页面、浏览器崩溃、或手机切走被系统回收 ——

- 已成功的 39 批被彻底遗忘，「继续发送」不可用；
- 用户唯一的出路是重新录入全部收件人再发一遍；
- 那会**对已经打过款的 39 批地址再打一遍**。

迁移前更糟：进度存在一个内存数组里，连批次表都没有。`DESIGN.md` 承诺过 TaskHub 断点续传，
代码里从来没有。

spec 002 刻意没修它（迁移不夹带改进），但为它铺好了路。本 feature 修它。

## 一个必须先答的问题：在途那批算什么？

假设崩溃发生在第 40 批**已发出、尚未收到结果**的瞬间。恢复时，这一批的真实状态是
**未知**的 —— 那笔交易可能已经上链，也可能根本没发出去。

这不是实现细节，是这个 feature 的核心难点：

- 当作「未发送」而自动重发 ⇒ 可能**重复打款**，正是要防的事。
- 当作「已成功」而跳过 ⇒ 可能**漏发一批**，钱没到但被记为完成。
- 两者都不做，把它单独标出来交给用户判断 ⇒ 安全，但把工作推给了用户。

本 feature 采用第三种作为**保底**，并在能自动判定时自动判定：`sendUserOperation` 在等待
收据之前就返回了 `userOpHash`，只是当前的进度回调没把它带出来。带出来并落盘，恢复时就能
去链上问一次「这笔到底成了没有」。

问不到（网络不通、外部钱包给不出凭据）时，退回「标为未知、由用户决定」——**绝不猜**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 崩溃后已打款的批次不会被再打一遍 (Priority: P1)

用户发送到 4000 个地址（40 批）。第 20 批完成后浏览器崩溃。重新打开页面，看到「上次发送未
完成」，选择继续 —— 前 20 批**一个都不重发**。

**Why this priority**：这是本 feature 存在的唯一理由。

**Independent Test**：给定一份已落盘的进度（若干批成功、若干批待发），恢复后触发续发，
断言只为未成功的批次发出请求。断言过程不涉及网络与钱包。

**Acceptance Scenarios**：

1. **Given** 已落盘的进度中第 0–19 批为成功、第 20–39 批为待发，**When** 恢复并续发，
   **Then** 只为第 20–39 批发出请求。
2. **Given** 同上，**When** 恢复完成，**Then** 界面显示已完成 20 批、剩余 20 批。
3. **Given** 一份**全部成功**的落盘进度，**When** 页面加载，**Then** 不提示恢复，
   该记录被清理。

---

### User Story 2 - 在途那批被单独标出，绝不被猜测 (Priority: P1)

崩溃发生在某一批已发出、结果未回的瞬间。恢复后这一批被标为「状态未知」，**不参与自动续发**；
系统尽力去链上确认它，确认不了就明确告诉用户，并给出两个动作：「已确认未到账，重发这一批」
或「已到账，标记完成」。

**Why this priority**：它是 P1 的另一半。没有这一条，恢复功能本身就会造成重复打款或漏发。

**Independent Test**：给定一份含「在途」批次的落盘进度，恢复后断言：该批状态为未知、
自动续发不选中它、且核心为它发出了一次确认请求。

**Acceptance Scenarios**：

1. **Given** 落盘进度中第 20 批为在途，**When** 恢复，**Then** 第 20 批状态为未知，
   且自动续发从第 21 批开始。
2. **Given** 同上且落盘中带有该批的交易凭据，**When** 链上确认它已成功，**Then** 它转为成功，
   不再需要用户干预。
3. **Given** 同上但链上确认它**未上链**，**Then** 它转为失败，成为可重试的批次。
4. **Given** 确认失败（网络不通 / 无凭据），**Then** 它保持未知，界面明确说明，
   并提供两个显式动作。
5. **Given** 一个未知批次，**When** 用户不做处理直接续发，**Then** 该批**不被发送**，
   其余待发批次正常进行。

---

### User Story 3 - 持久化先于花钱 (Priority: P1)

一批发出去之前，「这一批已被尝试」这件事必须先落盘。否则崩溃窗口正好落在「已发出、未落盘」
之间时，恢复后会把它当作从未尝试而重发。

**Why this priority**：它决定 P2 的「未知」区间是否完整。落盘晚于发送，就会有一批交易在任何
记录之外。

**Independent Test**：断言核心在发出批次请求之前先发出落盘请求，且只有落盘完成的回执到达后
才发出批次请求。

**Acceptance Scenarios**：

1. **Given** 一次发送即将开始，**When** 核心推进到某一批，**Then** 它先发出落盘请求，
   **并且**在落盘回执到达前不发出该批的发送请求。
2. **Given** 落盘失败，**When** 回执到达，**Then** 该批**不被发送**，发送暂停并告知用户
   —— 宁可不发，不可发了而不知道。

---

### User Story 4 - 恢复是可拒绝的，陈旧计划不会悄悄复活 (Priority: P2)

用户重新打开页面时看到「上次发送未完成」，可以选择继续，也可以丢弃。计划的年龄被显示出来。

**Why this priority**：一份三天前的计划，其收件人清单与余额可能都已不适用。默默恢复比不恢复
更危险。

**Acceptance Scenarios**：

1. **Given** 一份未完成的落盘进度，**When** 页面加载，**Then** 显示提示、未完成批次数与
   计划的创建时间，且**不自动开始发送**。
2. **Given** 用户选择丢弃，**Then** 该记录被清理，此后不再提示。
3. **Given** 用户开始一次**新的**发送，**Then** 旧的未完成记录被替换 —— 同时只保留一份。

---

### Edge Cases

- **落盘中的批次数与当前解析结果不一致**：恢复的是落盘的那份计划，与当前输入无关；
  两者不得混用。
- **恢复后用户切换网络/代币**：不影响已恢复的计划（计划在开始时就已冻结）。
- **同一批被确认为成功后又收到旧的失败回执**：以已落盘的终态为准，旧回执被丢弃。
- **落盘的收件人清单很大**（十万级）：恢复必须可用，且不得把整份清单送进视图。
- **确认请求本身超时**：视为「确认不了」，批次保持未知。
- **用户在未知批次上选择「已到账，标记完成」**：该批转为成功，**且不再发送**。
- **多个标签页同时打开**：后开始的发送替换记录；本 feature 不做跨标签页协调，
  但恢复提示必须反映磁盘上的真相而非内存。

## Requirements *(mandatory)*

### Functional Requirements — 持久化

- **FR-001**: 系统 MUST 把一次未完成发送的计划（网络、代币、精度、每批上限、单批费用、
  完整收件人清单、起始时间）与每一批的状态一并落盘。
- **FR-002**: 每一次批次状态的变化 MUST 触发落盘。
- **FR-003**: 一批的发送请求 MUST 在「该批已被尝试」这件事落盘**之后**才发出。
- **FR-004**: 落盘失败时，系统 MUST NOT 发送该批，MUST 暂停发送并告知用户。
- **FR-005**: 同一时刻 MUST 最多保留一份未完成的发送记录；开始一次新发送 MUST 替换它。
- **FR-006**: 全部批次达到终态（成功/失败）后，该记录 MUST 被清理。

### Functional Requirements — 恢复

- **FR-007**: 页面加载时，系统 MUST 检查是否存在未完成的发送记录，若有 MUST 提示用户，
  并 MUST NOT 自动开始发送。
- **FR-008**: 提示 MUST 包含未完成批次数与计划的创建时间。
- **FR-009**: 用户 MUST 能丢弃该记录；丢弃后 MUST NOT 再提示。
- **FR-010**: 恢复后，已成功的批次 MUST NOT 产生任何发送请求。
- **FR-011**: 恢复的计划 MUST 独立于当前的输入状态；两者 MUST NOT 相互影响。

### Functional Requirements — 在途批次的判定

- **FR-012**: 落盘中处于「在途」的批次，恢复后 MUST 被标记为**状态未知**。
- **FR-013**: 状态未知的批次 MUST NOT 参与自动续发。
- **FR-014**: 系统 MUST 为每个状态未知的批次尝试一次链上确认。
- **FR-015**: 确认为已上链且成功 ⇒ MUST 转为成功；确认为未上链 ⇒ MUST 转为失败（可重试）。
- **FR-016**: 确认不成功（无凭据、网络不通、超时）⇒ MUST 保持未知，MUST 明确告知用户，
  并 MUST 提供「重发这一批」与「标记为完成」两个显式动作。
- **FR-017**: 发送一批时，若能取得该批的交易凭据，MUST 在收到最终结果之前就把它落盘 ——
  这是 FR-014 能自动判定的前提。

### Functional Requirements — 边界约束

- **FR-018**: 落盘与读取 MUST 由宿主执行；核心 MUST NOT 直接访问存储。
- **FR-019**: 链上确认 MUST 由宿主执行；核心 MUST 只表达「请确认这一批」的意图。
- **FR-020**: 恢复的收件人清单 MUST NOT 进入对外视图。
- **FR-021**: 本次变更 MUST NOT 改变已迁移的 revoke 域，也 MUST NOT 改变 token-sender 在
  「无未完成记录」时的既有行为。

### Key Entities

- **未完成发送记录（PendingSend）**：一份冻结的计划 + 每批状态 + 起始时间。同时最多一份。
- **批次状态**：待发 / 在途 / 成功 / 失败 / **未知**（仅由恢复产生）。
- **交易凭据（BatchReceiptHint）**：足以让宿主去链上查一笔批次交易结果的标识。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 模拟崩溃（丢弃内存状态后重新初始化）并恢复，已成功的批次产生的发送请求数为 **0**。
- **SC-002**: 在途批次在恢复后为「未知」，且自动续发对它产生的发送请求数为 **0**。
- **SC-003**: 每一批的发送请求都晚于该批的落盘回执，顺序在用例中可断言。
- **SC-004**: 落盘失败时该批的发送请求数为 **0**。
- **SC-005**: 全部批次终态后，磁盘上不再存在未完成记录。
- **SC-006**: 恢复十万级收件人的计划，界面可用，且视图中不含收件人清单。
- **SC-007**: 无未完成记录时，token-sender 的行为与 spec 002 完成时逐项一致。
- **SC-008**: revoke 域与其余 12 个域行为不变，既有测试全绿。

## Assumptions

- **承接 spec 001/002 的全部架构决策**。核心不做 I/O；落盘、读盘、链上确认都是宿主请求。
- **存储介质沿用 IndexedDB**，与该域既有的自定义网络/历史同一套机制。
- **凭据的可得性因钱包而异**：biubiu passkey Safe 走 bundler，`sendUserOperation` 在等待收据前
  就返回 `userOpHash`；外部钱包（EIP-5792）给出的是调用批次标识。两者都可能取不到 ——
  取不到时走 FR-016 的保底路径，不猜。
- **不做跨标签页协调**：同时开两个标签页并各自发送不在本次范围内，但恢复提示必须读磁盘。
- **不改变「每批一次确认」的串行语义**。
- **陈旧计划不自动过期**：只显示年龄，由用户决定。设定过期时限需要单独的产品判断。
