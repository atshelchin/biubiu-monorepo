# Implementation Plan: 按域切分 WASM 产物

**Branch**: `004-wasm-per-domain` | **Date**: 2026-09-04 | **Spec**: [spec.md](./spec.md)

## Summary

先量清楚产物由什么构成（底座 112 KB / 各域 200–274 KB），据此确认「会随域数线性增长」，
再做两件事：

1. **两个编译期开关**（`wasm-opt -Oz` + `panic = "abort"`），省 4.1%。`strip = true` 实测反而
   变大 44.6 KB，弃用。
2. **按域切分产物**：一个 crate、每域一个 Cargo feature，构建脚本按清单逐个构建；
   页面只加载它用到的那一个。

判据是**每页下载量**，不是总字节数（research.md D31）。

## Technical Context

**Language/Version**: 同前。**不新增依赖。**

**Build**: `wasm-pack` 每域一次，产物落在 `src/lib/wasm/<domain>/`。清单
`rust/scripts/domains.mjs` 同时驱动构建与体积门禁。

**Testing**: 三个 spec 建立的全部测试必须保持通过 —— 这是一次交付方式的变更，不是业务变更。

**Constraints**: Vite 需要**静态可分析**的 `import()`，因此宿主侧的产物加载表必须是字面量。

## Constitution Check

| 原则 | 判定 |
|---|---|
| I / II / III / IV | 不涉及 —— 核心与宿主的边界不变，只改产物的组织方式 |
| **V** | PASS：核心测试不受影响（它们不经过 wasm） |
| **VI** | PASS：无业务行为变更；全部既有测试保持通过（FR-007） |
| **VII** | PASS：这条**就是**本 feature —— 门禁从单一阈值改为逐域，成本被逐域测量 |

## 实施顺序

1. 量：分别只导出一个域各构建一次，得出底座与各域的构成
2. 试便宜的：三个编译期开关，各自单独量
3. 切分：feature 门控 + 构建脚本 + 清单
4. 门禁：改为清单驱动、逐域
5. 宿主：`wasm-runtime` 按域缓存；每个 store 声明自己的域
6. 验证：构建产物里的 wasm 数量与体积、两页各自实际请求了哪一个、全量回归

## 已知风险

| 风险 | 处置 |
|---|---|
| 构建时间随域数线性增长 | 实测记录；域数多起来再考虑并行（results.md §3） |
| 底座在每个产物里重复 | 已量化（112 KB × 域数）；判据是每页下载量，重复是可接受的代价 |
| 新增域时漏改某一处 | 三处都会立刻失败（编译错误 / 运行时「未知的业务域」），不会静默 |
