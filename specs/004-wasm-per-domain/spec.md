# Feature Specification: 按域切分 WASM 产物

**Feature Branch**: `004-wasm-per-domain`

**Created**: 2026-09-04

**Status**: Draft

**Input**: `specs/002-token-sender-core/results.md` §2 的判读 —— 产物体积会随域数线性增长。

## 背景与问题

两个域进核心之后，WASM 产物 613 KB（本 spec 先做的两项编译期优化把它降到 588 KB，见下）。
spec 002 的判读是：主导成本不是数据，而是**每个域自己的机器**（serde 为每个线类型单态化出的
序列化代码），因此会随域数线性增长。

本 feature 先把这条判读**量实**，再据它决定。

### 实测：产物由什么构成

分别只导出一个域，各构建一次：

| 构成 | 字节 |
|---|---:|
| 共享底座（`crux_core` + `serde_json` + 泛型桥） | **111,668** |
| revoke 独有 | 202,368 |
| sender 独有 | 274,096 |
| 合并产物 | 588,132 |

判读得到证实：**底座只占 19%**，其余全是各域自己的线类型机器。剩下 12 个域按每个约 240 KB
（两个域的均值）估，合并产物会长到 **3.4 MB**。

### 那是每个页面都要下的

每个工具是一个独立页面，用户通常只用其中一个。合并产物意味着**打开撤销页面也要下载批量发送
的全部代码**。

| 域数 | 合并（每页） | 按域切分（每页） | 省 |
|---:|---:|---:|---:|
| 2（今天） | 588 KB | ≈ 350 KB | 41% |
| 4 | 1.06 MB | ≈ 350 KB | 67% |
| 8 | 2.02 MB | ≈ 350 KB | 83% |
| 14（全部迁完） | **3.45 MB** | ≈ 350 KB | **90%** |

切分之后每页的下载量**不再随域数增长**：底座 112 KB + 该域自己的约 240 KB。

代价是底座在每个产物里各存一份。对**跨页访问**而言这是重复下载：一个用户依次打开 k 个工具，
切分要下 k × 350 KB，合并只下一次 3.45 MB —— 交叉点在 k ≈ 10。没有人在一次会话里用十个工具。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 打开一个工具只下载这个工具需要的代码 (Priority: P1)

用户打开授权撤销页面。浏览器下载的 WASM **只包含撤销的业务规则**，不包含批量发送、也不包含
将来任何其他工具的代码。

**Why this priority**：这是本 feature 的唯一目的，也是唯一能阻止体积线性增长的手段。

**Independent Test**：构建后检查每个页面实际请求的 WASM 资源，断言它只对应该页面的域，
且其体积与「只编译该域」的产物一致。

**Acceptance Scenarios**：

1. **Given** 已构建的应用，**When** 打开撤销页面，**Then** 它请求的 WASM 只含撤销域，
   体积约 314 KB 而非 588 KB。
2. **Given** 同上，**When** 打开批量发送页面，**Then** 它请求的是另一个 WASM 资源。
3. **Given** 再迁入第三个域，**When** 打开撤销页面，**Then** 它请求的 WASM 体积**不变**。

---

### User Story 2 - 接入一个新域仍然只是几行声明 (Priority: P1)

维护者迁移下一个域时，切分不应成为新的负担：仍然是「Rust 侧三处 + 宿主侧两处」，
加上一处产物声明。

**Why this priority**：spec 001 的 SC-007 立下了「接入成本可预期」这条判据。切分若把它
变成一件麻烦事，就是用一个问题换另一个问题。

**Acceptance Scenarios**：

1. **Given** 切分已就位，**When** 接入一个新域，**Then** 新增的构建配置不超过一处声明，
   且不需要改动任何已有域。
2. **Given** 某个域的类型改了，**When** 执行常规构建，**Then** 只有该域的产物与契约被重建。

---

### User Story 3 - 已迁移的两个域行为完全不变 (Priority: P1)

撤销与批量发送的使用者感知不到差异。所有既有测试保持通过。

**Why this priority**：这是一次**构建与交付方式**的变更，不是业务变更。任何行为差异都是缺陷。

**Acceptance Scenarios**：

1. **Given** 切分完成，**When** 运行三个 spec 建立的全部测试，**Then** 全部通过。
2. **Given** 同上，**When** 在二进制模式下打开每个工具页面，**Then** 功能与切分前一致。

---

### Edge Cases

- **同一页面用到两个域**：目前没有这种页面。若将来出现，它会下载两个产物 —— 底座重复一次。
  这是可接受的，且比让所有页面都背上全部域更好。
- **底座本身变大**（例如升级 `crux_core`）：影响每一个产物。因此底座的体积必须被单独看住。
- **构建时间**：每个域一次 `wasm-pack`，构建变慢。必须实测并给出数字。
- **一个域没有被任何页面引用**：它的产物仍会被构建。需要一条明确的清单，而不是靠扫描。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 每个业务域 MUST 产出**独立的** WASM 产物，只包含该域与共享底座。
- **FR-002**: 一个页面 MUST 只加载它实际使用的那个域的产物。
- **FR-003**: 新增一个域 MUST 只需一处产物声明；MUST NOT 需要改动任何已有域的配置。
- **FR-004**: 契约生成 MUST 继续按域分子目录（spec 002 §5 建立的做法），MUST NOT 回退。
- **FR-005**: 体积门禁 MUST 改为**逐域**检查，且 MUST 单独盯住共享底座的体积。
- **FR-006**: 门禁 MUST 在新增域时无需改动即可覆盖它（清单驱动，而非逐个硬编码）。
- **FR-007**: 本次变更 MUST NOT 改变任何业务行为；已迁移两个域的全部测试 MUST 保持通过。
- **FR-008**: 宿主侧加载 WASM 的机制 MUST 保持产品无关 —— 每个域声明它要哪个产物，
  运行时缓存与初始化的逻辑 MUST NOT 按域复制。

### Key Entities

- **域产物（Domain Bundle）**：一个域的 WASM + 它的 JS glue，独立可加载。
- **共享底座（Shared Base）**：`crux_core` + `serde_json` + 泛型桥，在每个产物里各一份。
- **产物清单（Bundle Manifest）**：域名 → 导出类名 的对照，构建与门禁都读它。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 撤销页面加载的 WASM 体积 ≤ 330 KB（当前合并产物为 588 KB）。
- **SC-002**: 再加一个域后，撤销页面加载的 WASM 体积**不变**。
- **SC-003**: 每域产物的实测体积被记录，共享底座的体积被单独记录并设门禁。
- **SC-004**: 接入一个新域所需的构建配置改动 ≤ 1 处声明。
- **SC-005**: 三个 spec 建立的全部测试通过；二进制模式下每个工具页面功能不变。
- **SC-006**: 构建耗时的变化被实测并记录；若显著变慢，给出可执行的缓解方向。

## Assumptions

- **承接 spec 001–003 的全部架构决策**。切分只改变**产物的组织方式**，不改变核心与宿主的边界。
- **每个工具是一个独立页面**，用户通常只用其中一个 —— 这是切分收益成立的前提。
  若将来出现一个页面用多个域的场景，需要重新判断。
- **WASM 没有实用的动态链接**：底座无法被多个产物共享，只能各存一份。这是本方案的固有代价，
  已在上面量化（112 KB × 域数）。
- **不改变 JSON 边界与 `ts-rs` 合约**（spec 001 D3/D4）。缩减线类型数量是另一条独立的路，
  与本 feature 正交。
